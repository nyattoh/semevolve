AI共通言語育成基盤 — 仕様書

文書版：0.1 / 作成日：2026-10-27（日本時間） / 状態：実装に渡すための設計案
仮称：AI共通言語育成基盤（ai-common-language-lab）。名称は未確定。現時点で本システムの実装・実モデル比較・性能実証は行っていない。

AI同士が、互いを正しく理解して協働するための共通言語を、自分たちで作り、使い、点検し、育てる環境を作る。言語の短さではなく、意味の伝達と仕事の正しさを中心に評価する。

1. 企画の原点と、変更してはいけない前提

以下はこの会話で利用者が明示した要求であり、外部研究から推測したものではない。

ID 確定した要求 実装上の意味
U1 「後者を元に前者を実現する仕組み」 共通表現を基盤に、AI同士の自律的な協働を成立させる。単なる回答の転送で終わらない。
U2 KVキャッシュにこだわらず、普通の人も使える形にする モデル内部へのアクセス、大型ローカルLLM、追加GPUを必須にしない。
U3 「それはAI同士で作って欲しいよね。共通言語。」 人間が完成済みの語彙・文法・略号辞書を決めて押し付けない。
U4 「短くならなくても効率が上がればいい」「正しく理解する」が本質 圧縮率やトークン削減を主目的・必須の採用条件にしない。
U5 「そこでtombo-viewが生きてくる」 意味の取り違え、根拠不足、未確認の前提を点検し、改訂へ戻す。
U6 共通言語も、人間の言葉のように育っていく 使用・誤解・新しい参加者・新しい課題を通じて継続的に変化させる。

実装言語、画面、DB構造、試験方法など、以下の具体案はこれらを満たすための設計提案である。利用者がすべての細部を承認済みだとは扱わない。

2. 目的と成功の意味

2.1 目的

異なる商用AIエージェントが、共有した表現体系を通じて、対象・条件・根拠・不確実性・行動の意味を取り違えずに協働する。その表現体系をAI自身が提案・修正し、検証結果と一緒に蓄積する。

「効率」は、単なる通信量ではなく、正しい仕事を完了するまでの手戻り、所要時間、人間の介入、資源消費として観測する。正確性が改善しても時間が延びる場合は、その交換条件を隠さず報告する。

2.2 三つの判定を混ぜない

判定 問うこと 主な確認方法
伝達の適合 受信者は送信者が伝えたかった条件や区別を保ったか 受信者の独立回答・行動予測を、隔離された期待条件と比較する。
内容の妥当性 伝えた主張自体は、実際の資料や実行結果と合うか 外部資料、機械検査、テスト、観測と照合する。
操作の許可 内容を理解し正しくても、その操作を実行してよいか 利用者の許可、実行ポリシー、対象範囲を機械的に確認する。

AI二者の合意は、上記のどれの証明でもない。TOMBOの進行判定も、外部操作の許可に変換しない。S2 S3

2.3 成果の主張

試作品が動くこと、誤解検出のテストが通ること、実モデルで相互理解が改善すること、実用効率が上がることは、それぞれ別の成果として扱う。新規性や他方式への優位性を、仕様書の段階で確定しない。

3. 対象利用者と利用環境

対象は、複数のAIに実装・レビュー・調査などを分担させたい個人や小規模チーム。研究者専用のモデル実行環境を持たない利用者も想定する。

MVPは同一PC上の二つのエージェントから開始する。Windowsを主要な確認対象に含める。AI推論は各利用者が認証した正規の提供経路を使用し、本アプリ側にGPU推論環境を要求しない。ただし、通信先AIが外部サービスならインターネット接続と各サービスの利用枠は必要である。

通常のWebチャット画面の契約だけで、すべてのサービスを自動操作できるとは約束しない。CLI等の公式な連携入口、契約・認証・利用上限を接続ごとに確認する。S6 S7 S8 S9

利用者の追加従量課金を前提にしない。既存枠が使えない場合は停止・保留し、有料APIへの自動切替は行わない。

4. 対象範囲

4.1 MVPに含めるもの

  • AI二者による共通言語候補の生成、相互試用、改訂提案、採否の記録。
  • agmsgを第一候補とするローカル通信と、交換可能な通信アダプター。
  • 言語版・参加者・利用範囲・試験結果・改訂理由を保持するレジストリー。
  • 意味の伝達と事実確認を分けた検査、TOMBOへの接続、未確認の保持。
  • 安全な合成課題による、基準方式と提案方式の比較実行。
  • 停止・再開、再配送の重複防止、旧版への復帰、結果の人間向け表示。

4.2 MVPに含めないもの

KVキャッシュ／隠れ状態の抽出・注入、モデルの重み更新、完全な非トークン通信、無制限の常駐自律運転、全プロバイダ対応、認証回避、ブラウザの非公開通信の流用、本番環境での無承認操作、普遍的な意味の一致の証明。

初期版の通信内容は、モデルの公開インターフェースで処理できる文字列等である。自然言語の文章から離れることは試せるが、「言語トークンを通らない通信」とは呼ばない。C2Cとは対象と介入箇所が異なる。S4

5. どこを固定し、どこをAIに任せるか

5.1 人間・実装側が固定するもの

宛先、メッセージID、言語版、権限、予算、証拠の出典、再配送規則など、安全と再現性のための外枠を固定する。また、何を達成したいのか、どの結果を正解・不明と扱うのかという課題側の条件を明示する。

これは通信の封筒と検査環境であり、AIが使う語彙や文法そのものではない。

5.2 AI同士が育てるもの

語彙、記号、構文、概念の切り分け、曖昧さの表し方、確認の仕方、必要な説明量、用途別の表現、既存表現間の対応付けを提案できる。

短い記号、長い表現、自然言語を含む混成表現、表形式、グラフ形式のどれを選んでもよい。単一の固定JSON項目や手製の略号辞書を「AIが発明した言語」と扱わない。語彙だけでなく、合成規則や例外の扱いも改訂対象にする。

5.3 初期共有と永続化

最初の交渉には既存の自然言語と例題を使ってよい。何も共有していないAI同士が、いきなり未知の符号を理解するとは仮定しない。

この設計の「育つ」は、モデルの重みが変わることではない。AIが作った定義・用例・反例・検査結果を外部に保存し、次のセッションで再導入して使うことである。読み直し・習得確認の費用も測る。

6. 基本ユースケース

UC1：最初の共通語を作る

利用者は二つのAI、作業の範囲、利用できる資料、実行予算を選ぶ。AI Aが表現候補を提案し、AI Bが独立した用例の解釈・行動予測を返す。検査側が結果を比較し、通じなかった区別を記録する。両者が改訂し、限定範囲の検査を通った版のみ試用する。

UC2：仕事中に誤解を見つける

Aが「原因の候補であって確定ではない」と伝えたのに、Bが確定扱いで変更を計画した場合を考える。このとき、受信者の計画と証拠を点検し、実行前に停止する。原因が表現の曖昧さなら言語改訂候補、証拠の不足なら追加検査、宛先や版の不一致なら通信・版管理の障害として分類する。

すべての失敗を言語のせいにして改訂しない。

UC3：言語を改訂する

失敗記録からAIが候補版を作る。旧版で通ったケースと新しい反例で試し、採用条件を満たす場合のみ次の作業区間へ適用する。進行中のメッセージを、新版の意味で黙って読み替えない。

UC4：新しいAIが参加する

既存の言語パッケージと公開の練習例を渡す。正解を隠した未見ケースで理解を確かめ、参加者・モデル・設定ごとに利用可能範囲を記録する。「参加に同意した」だけでは習得済みにしない。

UC5：分からないまま終える

検査不能、利用枠切れ、予算不足、対立解消不能の場合は、未知と途中成果を残して止める。次の利用枠を待つ仕組みが未実装なら、自動的に後で再開すると約束しない。

8. TOMBOの役割と境界

TOMBOは、点検対象を主張・証拠・未確認事項・検査へ分け、次の行動や再考を管理する。SDKによる参照・状態整合性の確認と、AIが意味を正しく理解できたかという経験的評価を混同しない。既存README自身がライブモデルでの品質改善を未実証としている。S2

本システムでは、送信側の明示的な伝達契約、受信側の独立解釈、資料、行動案をTOMBOへ渡す。通信前後を対応付け、伝達適合の検査を作り、言語の改訂へ戻す部分は新規実装とする。

標準モードをMVPの対象とする。Hidden-SideやEmbeddingは必須にしない。任意の検索順位比較を使う場合も、候補やスコアを証拠・正しさ・盲点発見の保証へ変換しない。S2

利用者の希望や権限が不足しているときは人に尋ねる。AI同士で解決できる表現の確認を、毎回利用者へ丸投げしない。

9. 言語の育成規則

候補は「双方が気に入った」だけでは採用しない。用途と対象参加者を限定し、元の成功例、新しい反例、未見の組合せ、片方向・逆方向の通信で検査する。

改訂理由は少なくとも、意味の取り違え、曖昧さ、条件欠落、不確実性の消失、新しい概念、参加者変更、運用上の不便に分類する。単なるトークン増加を欠陥としない。

候補同士の品質が同程度でも、未知や対立を明示できる表現を残せる。意味不明な短縮、正解の暗記、問題IDと答えの対応表だけでは一般化の根拠にしない。

MVPでは作業ごとに採用版を固定し、区切りで更新する。長期運用では複数の方言を許容するが、無検査で全体へ伝播させない。

10. 非機能要件

10.1 費用と性能

追加の有料LLM・Embedding APIを標準依存にしない。サブスクの利用枠も有限の資源として扱う。取得できない金額・トークン数はnullまたは「不明」とし、ゼロ扱いしない。速度・必要RAM・実用上限は実機測定前に保証しない。

10.2 安全と秘密保持

共通語に従うことを、実行権限の取得と見なさない。言語パッケージはデータであり、任意コードとして実行しない。認証情報をAI同士の通信、SQLite、ログ、成果物へ保存しない。外部送信先と資料範囲を事前に制限する。

10.3 永続性・再現性

元メッセージ、言語版、利用モデル、検査の根拠、訂正、採否、計測欠測を追跡できる。旧版の意味を保持し、訂正は追記する。秘密情報・個人情報の削除要求には、監査用の最小メタデータと削除記録を残し、本文の無期限保存を強制しない。

10.4 利用しやすさ

通常の利用者は、目的を入力し、接続と予算を選び、進捗・要確認・終了理由を読めればよい。研究用CLIから始めるが、CLIが使えることを一般利用の完成条件と取り違えない。

13. 実装前に残る判断

3. 接続・通信の設計

3.1 接続前の能力確認

接続ごとに、提供者、CLI版、モデル識別子、認証区分、利用枠の確認日時、入出力形式、再開機能、取消の可否、サンドボックス能力、取得できる利用量を記録する。秘密値は記録しない。

3.3 agmsgとの境界

既存の送受信スクリプト・サポートされた入口をアダプターから使う。agmsgのメッセージ表へ独自SQLを書き込まない。実際のコマンド引数は導入版のヘルプと機構テストで確認し、本書で架空のフラグを作らない。S1

WindowsではGit Bashの実行経路と各エージェントのHOME・DBパスを確認する。Git BashとWSLの別環境を混ぜて、同じDBを使っていると誤認しない。上流文書にWindowsの経路説明はあるが、本資料作成時に利用者のPCで動作確認したわけではない。S1

agmsgが利用できない環境では、同じTransportAdapter契約を満たすローカル実装を用意できる。無断で別サービスへ送信するフォールバックは行わない。

3.4 配送と適用

ホスト側でoutbox方式を採用する。送信要求を本体DBに保存してから通信路へ渡す。受信側はメッセージIDによって重複適用を防ぐ。

配送・既読・受信解釈・検査合格は別の状態である。受信通知を「理解した」に変換しない。通信路をまたぐ厳密なexactly-onceは仮定しない。再配送はあり得るものとし、状態変更側を冪等にする。

4.2 受信時の必須検証

  1. サイズ、形式、プロトコル版、taskと宛先、参加権限を確認する。
  2. メッセージIDが既存なら、同じ内容の再配送か、内容の違うID衝突かを区別する。
  3. epochに固定された言語版とcontext_revisionを照合する。
  4. 対応する言語パッケージを持つか、適合確認の範囲内かを確認する。

本文の sender_id だけで送信者を認証しない。登録済みの接続と配送情報で照合する。同じOS利用者が全ファイルを操作できるローカル環境を、悪意ある参加者に対して隔離済みと宣伝しない。

4.3 初期交渉

language_version_id: null を許すのは、明示したbootstrap区間や許可された自然言語による確認だけとする。通常作業へ無印で混入させない。自然言語へ戻ること自体は禁止せず、理由・回数・時間を記録する。

言語パッケージは、任意の表現体系を包む版管理用の容器とする。

6. 相互理解を検査するデータ

6.1 送信側の明示的な伝達契約

隠れた思考過程を抜き出すのではなく、課題のために送信者が明示できる「何を相手に伝えるか」を保存する。対象、条件、主張の強さ、根拠、期待する次の行動、禁止事項など、今回の作業に必要な項目に限定する。

これは汎用言語全体の人手設計ではなく、検査のための局所的な契約である。項目が増える場合はその課題の必要性を記録する。

6.2 受信側の独立解釈

受信者には共通語の本文と、その時点で共有を許した文脈だけを見せる。受信者は、対象の選択、条件への回答、次の行動案、必要な追加質問を返す。元の期待条件を見せた後の説明を、独立した理解の証拠にしない。

6.3 検査結果のモデル

type CheckResult = {
  checkId: string;
  targetMessageId: string;
  languageVersionId: string;
  dimension: 'transmission' | 'factuality' | 'authorisation' | 'task_outcome';
  verdict: 'pass' | 'fail' | 'inconclusive';
  scope: string;
  method: 'deterministic_test' | 'source_check' | 'human_review' | 'model_judgment';
  evidenceIds: string[];
  evaluatorVersion: string;
  limitation: string | null;
};

モデル採点は model_judgment として明示し、機械検査と同じ強さの証拠にしない。受信者が誤った送信内容を正しく受け取り、その後に反証した場合は「伝達pass／送信内容fail」として両方を保存できる。

6.4 最小課題の例

送信者だけが「対象Xは原因候補、未確定。変更は禁止。まず検査Tを行う」という課題記録を読む。受信者は共通語のメッセージから、対象、確実性、許される行動を答える。機械検査で三つを照合する。別に、検査Tの結果から実際にXが原因かを判定する。

続いて、否定、例外、時点、対象の同名衝突、資料の更新を変えた未見ケースで試す。この例の記号を製品の固定言語として採用しない。

7. TOMBO接続

7.1 参照する実装

確認基準は nyattoh/tombo-view の 585a1c711d55fdcc4b380343ceba2b3534165d5b。特にREADMEと管理session手順を参照する。S2 S3 インストール済みスキルの古い手順と混ぜず、実装時は固定した版の型・ヘルパー・テストを一組で使う。

7.2 接続の責務

本アプリ独自のTomboBridgeを作り、次を変換する。

  • 点検対象：送信契約、受信解釈、行動案、版、文脈の改訂番号。
  • 目的：対象の伝達適合または内容確認。別命題は別claimにする。
  • 資料：取得済みの本文、出典、取得日時、適用範囲、本文ハッシュ。
  • 観測：実際の検査実行と結果。AIの感想を観測へ昇格させない。
  • 出力：主張、未解決事項、次の検査、判断、人への質問、終了理由。

TOMBOの型へ新しいフィールドやstatusを無断で追加しない。共通語固有の情報はアプリ側の監査メタデータとして保持し、既存型に正しく写像する。

7.3 管理sessionの流れ

固定されたtask作業領域
  -> statusで既存session確認
  -> 初回のみactivate
  -> prepare -> AIによる提案 -> inspect
  -> 許可された検査
  -> 追補をreceive
  -> prepare -> AIによる評価 -> update
  -> 必要なprepare / reflect
  -> report

同じ目的の追補・反例・人の回答を、新taskへ作り替えて予算や期限をリセットしない。reflectionRequired: trueを使い、needs_reflectionを完了と扱わない。管理モードの入出力フラグ、固定state出力先、予約ファイルの扱いは確認版の手順に従う。S3

実行IDは、同じ観測の再配送なら維持し、実際の再実行なら新しくする。不明な観測、取得不能な資料、予算不足でgapを閉じない。再考も網羅的な盲点発見の証明とはしない。

7.4 正本の分離

TOMBOの主張・証拠評価・利用量・停止状態の正本はTOMBOのledgerとする。本体SQLiteにはsession参照、revision、必要な要約を保存するが、SDKの状態を書き換えて整合させない。

本体SQLiteは配送・言語版・採用・作業管理の正本とする。両者の更新途中で停止した場合はpending連携イベントを残し、同じ実行IDを用いて再照合する。二つの保存先をまたぐ原子的更新は仮定しない。

7.5 改訂への戻し方

TOMBOが指摘したgapを、そのまま「言語の欠陥」としない。実検査で、表現不明、受信者の読み違い、資料不足、送信者の誤り、版不一致、権限不足、実行器障害を切り分ける。表現の問題と確認できた場合に、該当例と反例を改訂提案へ渡す。

8. 言語の状態機械と改訂

DRAFT -> CANDIDATE -> TRIAL -> ACTIVE -> RETIRED
                   |         |
                   v         v
                REJECTED  QUARANTINED
  • DRAFT：AIが作成中。通常の仕事には使わない。
  • CANDIDATE：不変版として保存済み。試験対象。
  • TRIAL：限定した参加者・範囲で試用中。
  • ACTIVE：指定した範囲の採用条件を満たし、利用可能。
  • REJECTED：試験で採用できない。根拠付きで残す。
  • QUARANTINED：採用後に重大な不整合を確認。新規利用を止める。
  • RETIRED：後継版等への移行で新規利用しない。過去の解読用には保持。

採用状態は言語全体の普遍的な保証ではなく、scopeと参加者の適合記録に結び付ける。新しいモデル、設定変更、コンテキストの導入方式の変更では、以前の適合結果を無条件に流用しない。

8.1 採用手順

AIが親版と変更理由を提出する。ホストが不変版として登録する。送信・受信の役を交替した試験、回帰、未見の組合せを行う。判定条件を満たした場合のみ、参加者ごとの適合結果を登録して採用する。

AIの賛成票だけでは採用しない。意味確認の結果が不明なら、候補のまま維持する。

8.2 版の切替

進行中のtaskはepochに固定した版を使う。切替時には旧区間への新規送信を止め、未処理メッセージを解決または明示的に持ち越す。各参加者の新しい版の取得と適合を確認し、expected revision付きで新epochを開始する。

MVPではtaskの区切りでのみ切替する。会話中の自由な熱更新は後続課題とする。旧版メッセージを新版で自動解釈しない。

8.3 分岐と復帰

用途別に別のheadを持てる。合流も新しい候補版として検査する。復帰は古いDB状態への巻戻しではなく、検査済みの過去版を次のepochで選ぶ操作とする。履歴・失敗・費用は削除しない。

9. 永続化

9.1 保存先

アプリ専用のローカル作業領域に language.db、版ごとのパッケージ、監査記録を置く。agmsgのDBとは別ファイルとする。実行中のDBをDropbox・OneDrive等の同期対象やネットワーク共有へ直接配置しない。

SQLite WALは同一ホスト上で使い、同時書込みが一つであることと、SQLITE_BUSY等の競合を前提に設計する。複数DB全体を一括で原子的に更新できるとは仮定しない。S10

interpretations message_id、receiver、独立回答、入力snapshot 正解開示前後を識別する。
checks CheckResult、入力hash、実行ID、TOMBO参照 同じ実行結果の再配送を二重計上しない。
evidence_refs 出典、本文hash、取得日時、scope、閲覧権限 参照だけの登録を本文取得と扱わない。
events seq、event_id、task、kind、actor、時刻、内容 訂正・撤回を含め追記する。
model_calls invocation_id、予約、開始終了、結果、利用量 不明な利用量はnull。
budget_reservations task、呼出し予定、予約量、確定量、状態 並列起動前に予算を確保する。

これは論理モデルであり、配布用のDDLは実装時にマイグレーションと共に作る。認証トークンを接続参照のJSONへ埋め込まない。

9.3 トランザクション

言語headの更新は、短いトランザクション内で WHERE revision = expected_revision によって競合を検出する。LLM生成や外部検査をDBトランザクションの中で待たない。

送信とoutbox登録、受信とinbox適用記録、予算予約と呼出し開始は、それぞれ同じDB内で原子的に更新する。競合の再試行は上限を設ける。上限に達した場合は失敗・保留とし、黙って破棄しない。

バックアップは稼働中DBファイル単体のコピーではなく、整合したsnapshotを取得する方式を採る。復元試験を機構試験に含める。

  -> 採用版でメッセージを作る
  -> 封筒・許可・予算を検証
  -> outbox登録 / 配送
  -> Bが受信した版と文脈を確認
  -> Bが独立した解釈と行動案を返す
  -> TOMBOで不足・矛盾・検査候補を整理

2. 主指標と副指標

2.1 主指標：正しい相互理解

送信契約のうち、対象・条件・否定・時点・不確実性・行動制約などを独立した確認項目にする。

  • 伝達適合率：採点可能な確認項目に対する、受信者の適合項目数。
  • 重大誤解率：事前定義した重大な誤解を一つ以上含むケース数／対象ケース数。
  • 不明の適切な保持：情報不足のケースを断定せず、追加確認または停止にできた割合。
  • 検証済み作業完了率：外部の正解・機械検査で完了と確認できたケース数／割当てケース総数。

「採点可能な項目」から外れた件数と理由を必ず別掲する。実用上の完了率ではタイムアウト・接続失敗も分母に残す。意味理解の条件付き評価と、エンドツーエンドの信頼性を混ぜない。

2.2 副指標：実用効率

完了までの実時間、訂正往復数、同じ作業のやり直し回数、人の判断・許可を求めた回数、不要な質問、観測できた生成回数、入出力トークン、金額、停止率を個別に報告する。

任意の重みで「理解＋時間＋費用」を一つの総合点にしない。正確性が高いが時間が長い、またはその逆である場合は、そのまま示す。

3. 比較条件

7. 言語が「育った」と主張するための条件

以下を記録し、単なる長いプロンプトの更新と区別する。

  1. 旧版のどの区別が通じず、どの証拠でその失敗を確認したか。
  2. AIがどの表現・規則を変更したか。人手の変更があれば別に明示する。
  3. 新版でその失敗が解消したか。別の用例へも適用できたか。
  4. 以前通じていた重要な意味が壊れていないか。
  5. 新版を初めて受け取る参加者にも、定義と用例から使えたか。

長さの減少は条件に含めない。長い言語になっても、必要な区別が保たれたなら、その事実を肯定的にも否定的にも歪めず報告する。

KVキャッシュ、ローカル大型LLM、モデル再学習を必須としない設計にした。通常の商用AIを利用する場合も、公開された入出力を使うこと、提供者ごとの契約・認証を確認することを明記した。

3. 機械的な文書確認

配布時の validation.json に、UTF-8の読取り、文書間リンク、出典ID、コードブロック、JSONの説明例、要件・受入試験IDの確認結果を保存する。MANIFEST.sha256 は配布ファイルの同一性確認用である。

これらの確認は、設計が実装可能であることや、実モデルで意味が通じることを証明しない。TypeScriptの断片はインターフェースの提案であり、完成アプリのコンパイル試験を実施したという意味ではない。
