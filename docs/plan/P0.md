## 1. 固定したgoal charter

言語の語彙・文法や保存分解を固定SVOへ縮めない。構造維持も候補として扱う。公開fixtureの成功をAIの理解改善、言語発明、自律保存設計、未見例への一般化の証拠にしない。伝達、内容、許可、保存忠実性、最終結果を分ける。実モデルはP1以降であり、P0の能力評価には含めない。

- S0は本計画、workspace設定、共有型、contract試験、schema、CI、CLIとlocal-uiの骨格を所有する。00〜07の正本、既存TOMBO、既存agmsg DBを変更しない。本体機構は後続ownerが実装する。
- S0以降の後続実装はrootが証拠と本書を検査して別途依頼する。delegated goal PMは計画・証拠照合を担い、製品コードを実装しない。root PMがdispatch、共有owner、レビューと統合順を管理する。
- 第一PRは全パッケージの型・インターフェース・テスト基盤・CIを含む骨格1本。ゲート通過前に後続writerを開始しない。
- 後続は別branch・別worktree・別Draft PR。最大3writer。merge禁止のため、レビュー済み骨格headの子孫を基点とするstackで進める。
- 全PRでBugbotの実runが必要。無効・skipなら即停止。Codex/Bugbotの新指摘に設計判断が必要なら、利用者へ決める内容を1行で問い、停止する。機械的修正のみ範囲内で扱う。テストを緩めない。

### 永続化のP0案

`core` にstore portとtransaction契約を置く。本番DB選択を避けるため、P0専用のファイル永続アダプタを分離して実装する案とする。隔離した一時領域内の単一writer、原子的なbatch記録、追記journal、検証済みsnapshotと再生によって参照実装を作る。複数クライアントの予約・CASは同一writerへ集約し、二重writerの起動は拒否する。ライブownerを奪わず、異常終了後のowner判定と復旧を試験対象とする。

これは製品DBの選定や任意DBでのtransaction保証ではない。Node22/Windows/Linuxで実プロセスを終了・再起動し、永続データから復旧する試験が必須。journal途中書込み、snapshot切替前後、確定後応答消失、破損を注入する。破損を黙って切り捨て成功とせず、復旧不能は停止する。電源断、全filesystem、ネットワーク共有、悪意ある同一OSユーザーへの安全性は未検証と明記する。実装の複雑さが契約を満たせない場合は本番DBを黙って選ばず、代替のP0試験用アダプタをrootへ戻す。

## 4. 所有ファイルと依存DAG

S0後に永続基盤Cを1ownerで通す。R/P/Tがそれぞれ独自のtransactionやID契約を作る衝突を防ぐため、推奨分割へこの直列段階を加える。EとLは凍結した検査portを共有し、Lの単体試験では公開の決定論的検査doubleを使う。実際のEとの結合はIで検査する。

```text
S0 骨格・全境界型・テスト基盤・CI
  └─ gate(S0) ─ C 共有契約実装・永続基盤
                  └─ gate(C) ─┬─ R registry ─────────┐
                               ├─ P policy + fake ──┤
                               └─ T transport ──────┘
                                   各PR gate + J1統合head検査
                                           ├─ E evaluator + tombo bridge ─┐
                                           └─ L storage planner ──────────┘
                                                各PR gate + J2統合head検査
                                                        └─ I CLI・全機構統合
                                                            └─ root最終照合
```

J1/J2はroot管理の逐次統合作業。製品ロジックの追加を混ぜず、統合時に新規修正が必要なら該当ownerへ戻す。EはR/P/T/Cを使う。LはR/P/CとEの凍結済みportに依存し、Eの完成を単体実装開始条件にしない。Iは全単位に依存する。全てのgateは対象headに対するTDD・回帰・独立review・CI・Bugbotであり、承認済み旧headの結果を新headへ自動流用しない。

## 6. mergeせずstackを作る計画

**依存worktreeの基点指定は後続開始前に確認する。** ホストの作成機能が検証済みheadを基点にできるかは未確認。プロンプトのpathだけでbindingを代用しない。

6. 統合時の機械的競合だけを既存変更を保持して解消する。設計選択が必要なら停止する。移植後のheadで回帰・独立レビュー・Bugbotを再確認する。元PRの合格だけをJ1/J2合格へ転用しない。

## 8. TDD・独立review・Bugbot停止ゲート

各実装workerは環境の必須スキルを自分で読み、host-adapter、対象playbookと必要なleaf skillを参照する。親の要約だけで読了としない。potetoの既定モデル、追加fan-out、shell worktree、非Draft、merge、watch loop等が本依頼又は現行T3規則と衝突する場合は、本依頼・現行host規則を優先する。workerからの追加子dispatchは付与しない。必要なreviewはrootが独立taskで起動する。

全workerのbriefにはgoal、所有パス、read-onlyパス、親head、契約revision、対象AT、失敗条件、実行費用/秘密制限、stop gateを入れる。「他の編集者がいるため既存変更をrevertしない」と明示する。着手時に実cwd/binding/branch/HEAD/statusを確認し、不一致なら書込みを止める。

1. テストを書き、未実装又は対象欠陥が原因のactual REDを実行する。環境起動失敗や不正なテストだけのREDを代用しない。
2. 最小実装で同じテストをGREENにし、関連regressionを実行する。正確なcommand、cwd、exit、件数、head、artifact hashを保存する。
3. 実diff、base/head、対象ファイル、元charter、AT、RED/GREEN/regression証拠を読めるhandover artifactにまとめる。
4. rootはfresh `delegate_task(role: review)` を使用し、実装者と異なるvendorをlive catalogueから選ぶ。`assign_slot.py --layer main --role test_integrate --avoid-vendor <実装vendor>` 等で候補を選び、実呼出しのprovider/model/optionsを保存する。catalogue存在は起動成功の証明ではない。
5. reviewerは書込みをせず、実diffと試験を読み、`pass / fail / needs_review` を返す。同vendorしかない場合でも、本計画のcross-vendor必須を自動免除しない。rootが利用者へ判断を戻す。
6. 機械的修正は所有者が行い、影響する試験とfresh reviewをやり直す。新reviewには過去指摘・対応・未解決異議を渡す。最大2修正/review roundで解消しなければ停止して判断を求める。Codex/Bugbotの設計指摘はround上限を待たず即停止。
7. 全Draft PR、J1/J2を含めてBugbotのrun ID/URL、head SHA、完了状態、指摘を記録する。チェック名の存在、インストール推測、HTTP 401、botの無言を実run成功としない。無効/skipなら即停止し報告する。pending/未確認ならゲート未達として依存作業を開始しない。
8. 作成・引受け・pushしたPRは直後に `link_pull_request` を呼ぶ。check/review待ちの監視はrootだけが `watch_pull_request` を使う。子はwatchしない。sleepやpoll loopで監視を代用しない。

停止時の1行例は「新指摘で未確定予約を解放する設計変更が必要です。unknownを維持する現契約を変更しますか。」とする。具体的な指摘と選択だけを問い、回答前に依存処理へ進まない。試験成功のためにexpected値・対象・fail条件を弱めない。

### hashの契約

HostIdentity.digestはSHA-256の小文字hexを返す設計。対象JSONはUTF-8、object keyは再帰的にUTF-16 code unitの辞書順へ並べ、配列順は保存し、空白なしのJSONで表す。文字列はUnicode正規化せず、numberはJSON.stringify表現、負の0は0。非有限数、undefined、疎配列、非JSON objectを拒否する。実装と正負のcanonical testはCが担当する。

Envelope digestは全Envelope fieldを対象とする。LanguageVersion digestはLanguageContent全fieldを対象とし、host生成のversion_id、digest、採用status event、conformance履歴は除く。同じ版IDでcontentが変わる場合は拒否する。TaskStoreのexpectedDigestはentry.value、snapshot digestはdigest field以外のsnapshotを対象とする。ハッシュ一致は内容同一性だけの検査で、意味理解や採用の証明にはしない。

公開APIは `hostIdentity`、`canonicalJson`、`digestJson`、`parseEnvelope`、`createMemoryTaskStore`、`openFileTaskStore`。承認された修正として `EnvelopeRejection` に `digest_mismatch` を追加する。他の既存契約型は変更しない。`parseEnvelope` はwireと信頼済みの `EnvelopeContext` を照合し、escape復号後の同一JSON member名の重複を `invalid_format` で拒否する。保存済digestを第3引数に渡した場合はその一致も検査し、不一致は形式不正とは別の `digest_mismatch` で返す。parserだけでは既存message IDとの内容衝突と断定しない。同ID別内容の適用・監査はTransport、言語パッケージ取得・scope適合はRegistryの責務である。

両storeは同一の宣言的transaction実装を使う。collectionは既定でinsert専用とし、ホストが構築時の `mutableCollections` で指定したcollectionだけをdigest CASでreplaceできる。fileを再開する際も同じ設定を要求する。domain型への変換と、各ownerが扱うcollectionの選択はそのownerの責務。原本と訂正の両batch、拒否結果、transaction IDと結果はjournalへ保持する。

file adapterはP0の隔離されたローカル一時領域専用。複数クライアントは一つのwriterへ接続する。別writerによる同じdirectoryのopenは拒否する。既定の待ち行列上限は64。満杯の要求は受付前の `unavailable`、CAS敗者は `revision_conflict` として再試行せず返す。正規batchの成功・保存拒否結果をjournalへsyncし、独立した `journal-tail.json` のrecord数・末尾digestを一意な一時fileへのwrite/sync、rename、対応OSでdirectory syncの順で確定してから応答する。同transaction IDの再配送では元の結果を返す。I/O失敗後は結果を推測せず使用を停止し、close・再openによる正本照合を要する。

`inspectFileStoreOwner` で取得したtokenを `recoverFileStoreOwner` に明示して異常終了後のlockを回復する。同一hostのPIDが不存在と確認できた場合だけlockを外す。ライブPID、PID再利用、権限不足、壊れたowner情報、回復途中のguardは停止条件。PIDの期限だけでownerを奪わない。

`checkpoint()` は整合snapshotを新しい一時fileへ書いてsyncし、renameで切り替える。元journalを切り詰めない。起動時はjournal全体のhash連鎖とtransaction結果を再検証し、snapshotがその履歴の一地点と一致することに加え、最終record数と末尾digestが独立tail記録と一致することを要求する。tailの欠落・破損・不一致は拒否し、tailのない旧P0 directoryも自動移行しない。`backup(newDirectory)` はwriterの待ち行列内でjournal、対応snapshot、tailを新規directoryへ保存する。復元先を通常のopenで検証し、transaction結果も保持する。TaskStoreのsnapshot値だけでは再配送結果の履歴を含まないため、永続復元にはこのbackupを使う。未切替の一時file、途中journal、破損fileは削除しない。

故障試験は実子processをcommit前、journal途中、journal同期後、tail切替前・切替と対応OSのdirectory同期後、commit後応答前、snapshot切替前後で停止する。journalだけ先に確定した窓ではtail不一致としてopenを拒否し、未応答結果を成功へ推測しない。tail確定後は同IDで再照合する。独立tailが保持される範囲では、checkpoint以降の応答済み成功・保存拒否recordを含む完全な末尾欠落も検出する。journal・tail・snapshotが整合した過去状態へ同時に失われる場合や、同一OS利用者が証跡も整合して改変する場合の検出は保証しない。未応答recordとjournal先行差分がともに失われ旧tailと一致した場合、そのrecordの存在は証明できない。

競合試験では二つの子clientがそれぞれ別のloopback socketでtest writerへ直接batchを送り、直接結果を受け取る。親は起動・go・観測だけを制御しbatchを中継しない。writer内の最初のappend前に先着要求を保持し、後着の `transact` 呼出し後に二つのPromiseが未解決である観測列を検査してから解放する。CAS・残量1の両試験で、勝者1件、敗者の `revision_conflict`、再起動後の両receiptとsnapshotを照合する。同じ試験は、prepareをwriter queue外へ移した非原子mutantの二重成功と、敗者を `unavailable` に誤分類するmutantを検出する。旧親IPC中継試験の成功は、この実overlapの証拠としては使わない。これは一般store原子性の試験であり、Policyによる実invoke制御の証明ではない。socket listenerはテスト専用で、本番通信路の選定ではない。

完全な末尾欠落の試験では、headerだけへ切り詰めるケースをcheckpointなしで実行する。checkpointによる既存の拒否をtail検出の証拠に数えない。旧fixtureはheader-only時にもcheckpointを作ったため、旧実装では4件中3件が欠落後にopen成功し、残る1件はsnapshot不整合で既に拒否されていた。旧記録の「4件ともopen成功」は訂正し、原記録を保持する。修正fixtureは旧file-storeで4件ともopen成功を検出するREDとなり、tail付き実装では4件とも拒否するGREENになる。

接続12ケースは、出力を含むstate、初回receipt、同ID再配送とfake起動抑止、ID衝突監査、未知版・digest不一致・隔離版、旧epochとheld整合、自己申告・fingerprint変更、各grant、provider経路、残量1の予約競合、null usage・timeout・応答消失、期限・取消、取消非対応の後着settlementを検査する。競合では実store.transactを観測用に包み、同じexpectedRevisionの予約2件が未解決であることを確認してから実writerを解放する。実transactionの戻り値は変更しない。

再起動7試験は別Node processでreceiptのみ保存後の再配送、保存済み全domainの再照合、予約commit後killと死んだownerのtoken照合・回復、unknown三種、期限・取消と旧epoch保留を検査する。processごとのPID、到達境界、終了code・signal、snapshot digestは非公開証拠に記録する。再open時にtaskを再登録して開始・予算をリセットしない。

局所helperの実装TDDでは、実factoryによる配送・受信後、未実装の適用接続によりstateが空になるassert失敗を記録し、Policy.executeとapplyの接続で同じassertを成功させた。Registry無視、send grant無視、Policy replay抑止除去の3種類は別の機構検出である。process内loaderだけで変異し、予定したassert失敗と無変異の再成功を確認する。変異失敗を実装REDへ転用していない。
