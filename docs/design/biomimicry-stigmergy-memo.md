## 0. 一言で

「能力を全部載せた1体」より「専門エージェントの生態系」。ただし生態系が効くのは、**共有の黒板・ポインタ渡し・LLM外の関所**という仕組みがあるときだけ。人数を増やすこと自体は効かない（§8 の 81i）。

## 1. 村の共有記憶をスティグマジー黒板にする [仮説]

エージェント同士が直接メッセージを送り合う代わりに、共有の黒板に「シグナル」を置き、各エージェントはシグナルの強さに反応して動く。

### 1.1 形式

- 追記専用 JSONL（1行1イベント）。更新・削除は行わず、減衰や解除も新しい行で表す。
- `path_key` で場所を表す（例：`task/81i/bpm-detect`、`repo/apps/cli/src/hub.ts`）。Gemini 案の `locus` に相当。
- 本文は載せない。`payload_ref` に置き場所（hub の message id、ファイルパス＋commit、PR番号など）だけを書く。

```json
{"signal_id":"sig_0001","path_key":"task/81i/bpm-detect","type":"SUSPECT","emitter":"agent:A","intensity":0.4,"decay_rate":0.1,"ttl_s":3600,"payload_ref":"hub:msg/abc123","at":"2026-11-03T17:00:00+09:00"}
{"signal_id":"sig_0001","op":"AMPLIFY","emitter":"agent:B","delta":0.5,"payload_ref":"hub:msg/def456","at":"2026-11-03T17:05:00+09:00"}
{"signal_id":"lock_0001","path_key":"task/81i/bpm-detect","type":"CLAIM_LOCK","emitter":"agent:C","ttl_s":900,"at":"2026-11-03T17:06:00+09:00"}
```

### 1.2 ルール

- **強さ**：現在値は読み出し時に計算する（`intensity × (1 − decay_rate)^経過tick ＋ Σ delta_i × (1 − decay_rate)^(delta_i の時刻からの経過tick)`）。AMPLIFY の加算分もそれぞれ自分の時刻から減衰させ、古い AMPLIFY が TTL まで満額で残らないようにする。TTL を過ぎたら 0。計算は黒板側（決まったコード）で行い、LLM にはさせない。
- **CLAIM_LOCK**：閾値を超えた `path_key` に着手するエージェントは、先に CLAIM_LOCK を置く。有効なロックがある `path_key` には他のエージェントは着手しない。ロックは TTL で自然に切れる（落ちたエージェントが握りっぱなしにしない）。
- **ポインタ渡し**：エージェントは `payload_ref` を見て、必要なときだけ本文を取りに行く。全文の回覧をやめてトークンを減らす狙い。効果は §9 で測る。
- 既存の `records` / `deliveries`（SQLite）と二重管理にしないため、最初は hub の外の JSONL で試し、効果が出たら取り込みを検討する。
- Memory Tax の方針（要約には生ログへの経路を残す）と相性がよい。`payload_ref` がその経路になる。

## 2. 中央（PM）は大域パラメータだけを調整する [仮説]

PM はエージェントに細かい指示を出さず、次の「環境レバー」だけを動かす。

| レバー | 例 |
|---|---|
| 予算 | タスクごとのトークン上限・時間上限 |
| 閾値 | 着手に必要な `intensity`、監査に回す条件 |
| 減衰・TTL | 古い仮説を早く消す／長く残す |
| 編成 | single / team / cheap_swarm の選択（§7） |

マイクロ指示（「A は X をやれ」）は PM のトークンと待ち時間を食い、PM が詰まり点になる。PM の仕事を「パラメータと編成の選択」に絞る。

## 3. メタ認知を探索役と監査役に分ける [仮説]

| 役 | すること | 権限 |
|---|---|---|
| 探索役 | 「他の問題は？」「目的に合っている？」を問い直し、シグナルや提案を出す | 提案のみ。実行しない |
| 監査役 | 提案と成果物を、目的・規約・安全の観点で独立に検査 | 差し戻し・凍結（veto） |

- 監査役は探索役と別コンテキスト（別セッション・可能なら別モデル）で動かし、同じ思い込みを共有しないようにする。
- 81i の反省（§8）にそのまま効く想定：「テストは通るが曲で動きが変わらない」を見つけるのは、目的に照らして成果を見る監査役の仕事。「目的に沿っている作業」と「目的を達成した作業」を分けて判定する。

## 4. 実行時の決定論的ハーネス [仮説・一部外部確認]

安全はプロンプトの心がけに頼らず、LLM の外の決まったコードで止める。

- **書き込み前ゲート**：黒板への追記前に、スキーマ検査・送信者の照合・1エージェントあたりの書き込み量上限。
- **公開前マスク**（仮説）：黒板への書き込み時に、ユーザー名とローカル絶対パスを置換するか、書き込みそのものを拒否する。既存の `scripts/check-public-artifacts.mjs` は流用しない。この検出器はドライブレター付きパスと `/Users|home/<name>/` しか拾わず、問題を報告するだけでマスク済みの内容を返さないため、書き込みゲートには足りない（Codex指摘、PR #14 discussion_r4452304454）。
  - 専用の sanitizer を用意し、少なくとも次の形を対象にする：ドライブレター付きのパス、UNC パス（サーバー名と共有名で始まるもの）、POSIX の絶対パス全般（ホーム・作業ディレクトリ・一時ディレクトリを含む）、チルダ始まりのパス、単独のユーザー名。
  - 既知の場所は `%USERPROFILE%` / `%TEMP%` などのプレースホルダに置き換える。置き換えられない絶対パスが残る書き込みは拒否する（fail closed）。
  - 上の各形について、マスクされることと拒否されることをテストで確かめてから有効にする。
- **ツール実行前ゲート**：Claude Code の PreToolUse フックと同じ位置付け（実行直前に許可/拒否を返す）[外部確認：https://code.claude.com/docs/en/hooks]。semevolve では provider adapter の実行直前に置く。
- **Policy as Code**：許可条件をコード（最初は TypeScript の純関数、必要なら OPA/Rego）で書き、テストで固定する。
- **追記専用の監査ログ**：誰が・どのシグナルを根拠に・何をしたか。

根拠：OWASP Top 10 for Agentic Applications 2026 の ASI06（Memory & Context Poisoning：共有メモリ経由の汚染の伝播を含む）と ASI08（Cascading Failures：1つの不具合の連鎖・増幅）。対策として記憶書き込みの検証、出どころの記録、予算・回数上限、サーキットブレーカーが挙がっている [外部確認：https://genai.owasp.org/download/52117/]。共有黒板はまさに ASI06 の攻撃面なので、書き込み前ゲートは必須とする。

## 5. リスクティアと人間の手綱 [仮説]

Kota が手綱を持つ点を、ティアに対応させる。

| ティア | 例 | 扱い |
|---|---|---|
| 0 読むだけ | 調査、黒板の閲覧、ローカルの試行 | 自律 |
| 1 戻せる変更 | ブランチ作業、ドラフトPR、黒板への追記 | 自律＋監査ログ |
| 2 影響の大きい変更 | 予算上限に近づく実行、ガードレールに近い変更の提案 | 監査役の検査を必須 |
| 3 人の承認が必須 | **不可逆な操作**（merge、公開、送信、削除、購入）、**予算上限の変更**、**ガードレール（ハーネス・ポリシー）の変更**、**目標の変更** | Kota の明示承認がない限りハーネスが拒否 |

ティア判定はエージェントの自己申告ではなく、ハーネス側の規則で決める（自己申告は甘くなる）。

## 6. O(N²) を避けてスケールする [仮説]

- 全員が全員に話すと経路は N(N−1)/2 本（10体で45、100体で4,950）。
- 黒板方式なら各エージェントは黒板との読み書きだけ。PM は統計だけを見る。
- エージェントの入れ替え（Kota の「村・家族」像：個体が替わっても文脈が続く）も、状態が黒板にあれば容易になる。

## 7. チームかシングルかの振り分け [仮説・実装は未merge]

bench-ledger-router PR #5（https://github.com/nyattoh/bench-ledger-router/pull/5 、**未merge**）の `choose_arm.py` と `actual_runs` を使う。

- 派遣前に `choose_arm.py --task-kind <kind> --difficulty <d>` を呼び、single / team / cheap_swarm を選ぶ。
- 証拠が足りない間は single（PR の既定動作）。team や cheap_swarm は、成功率が single より高く、トークン中央値が上限（既定2倍）以内のときだけ選ばれる。
- 実行後は `record_actual.py` で `actual_runs` に tokens・時間・テスト結果・人間の判定を記録する。
- 81i の結果（§8）を入れると、少なくとも「小さい実装タスク」は single に寄る見込み。
- 専用の振り分けエージェントは足さない（Kota の方針：PM や各エージェント自身が判断できるかを見る）。

## 8. 根拠になった実測：decision81i [実測]

音楽ファイルの BPM を推定して文字を拍に合わせて揺らす小さな静的 Web ページ。

| アーム | tokens | 時間 | テスト |
|---|---:|---:|---|
| single | 5,942 | 126 s | 13/13 |
| team（3体） | 39,884 | 509 s | 13/13 |

- team は tokens 約6.7倍、時間約4.0倍で、テスト結果は同じ。
- どちらも「曲を変えても動きがほとんど変わらない」ことに気づかず、直さなかった（Kota の指摘）。PM は「当たり」判定を取り下げた。
- 言えること：この1課題では team の利点は見えない。言えないこと：team が一般に劣ること（標本1件）。

## 9. 最小の測定実験：ポインタ渡し ON/OFF [提案]

- **問い**：エージェント間で本文を回す代わりに `payload_ref` だけ渡すと、tokens と時間は減るか。品質は落ちないか。
- **条件**：同じ小課題・同じ編成（team 3体）・同じモデル/effort で、
  - OFF：現行どおり本文を渡す
  - ON：黒板（§1）に `payload_ref` だけ書き、必要時に取得
- **記録**：各 run を `actual_runs` に入れる（`run_id` は `semevolve:<decision>:<arm>:<role>`。arm 名に `ptr-on` / `ptr-off` を含める）。tokens、hostDurationSeconds、テスト件数、人間の判定。
- **回数**：各条件2回以上（`choose_arm` の `min_samples` 既定値に合わせる）。粒度は事前に固定し、追加試行で延々と続けない。
- **判定**：ON が tokens を減らし、テスト結果と人間判定が OFF 以上なら採用候補。品質が落ちたら、ポインタ取得の判断（いつ本文を取りに行くか）を先に直す。
- **やらないこと**：この実験では監査役・ハーネスは足さない（変数を1つにする）。
